## 0. 背景:前提已变,拆分合并降级

原规划假设「内网弱模型 + 两万字逐字稿 ≈ 必须拆分合并」。前提已变:内网已部署 GLM 5(**128K 上下文**),两万字中文 ≈ 2 万 token,仅占窗口 ~1/6 —— **块级拆分合并是小窗口时代的补丁,v1 不做**,由 SPEC-INS-017 §5 埋点(chip 点击中超阈值占比)决定是否立项。名义 128K 按**舒适区 ~60K** 做预算(内网蒸馏版长文本中段召回衰减待评测,见 §7)。

v1 形态:**单文档直喂 + 多文档 task 子代理分治 + 超阈值走 MCP chip**。三条路覆盖后,自定义拆分 pipeline 没有 v1 必须做的场景。

## 1. 范围

- 第一个能力:**观点解析**(与 MCP `key_findings` 同类,本地即时完成、免排队)。
- 单文档:extract_document 抽文本 → 模型在上下文内直接分析(不进子代理,保住迭代追问体验)。
- 多文档:每文件一个 task 子会话做 map,父会话 reduce(§5)。
- 能力形态:**零新增解析 tool、零新增用户入口**——对话即能力(§2.5);「研究工具」chip 维持 017 现状。
- 产物:markdown 落 `insight/<sessionId>/outputs/` + 对话内摘要(§3)。
- 护栏:超阈值提醒不中断(§6;017 落地后仅为建议话术)。

## 2. 输出契约(能力线第一等公民:出处引用)

观点解析产出结构(markdown,人读 / 卡片渲染 / 父会话 reduce 三用):

```markdown
# 观点解析:<源文件名>
## <分组名>
- **<观点一句话>**(<发言人>)
  > 原文:「<引语>」 —— <源文件路径> · [P37]
```

- **出处引用是硬性字段**:观点 → 发言人 + 原文引语 + **段落锚点** + 源文件路径。这是本地线相对 MCP 的差异化能力(报告经得起「结论哪来的」质问),也是多文档 reduce 时的去重锚点与父会话追问时的定点回读入口。
- **段落锚点(2026-07-11 新增)**:extract_document 输出正文时给每个段落编号(`[P1]`、`[P2]`…全格式统一,docx 按段、pdf 按页内段、xlsx 按工作表行块、pptx 按页)。产物引语必须带锚点——它把引用从"软约束"变成可程序定位的硬字段(§2.6 校验器的地基),也让追问回读从"全文重灌"变成"按锚点附近定点 read/grep"。
- 与 MCP 产物格式的对齐程度:不强求同构(MCP 产物结构是他们团队的契约),但卡片渲染路径尽量复用 —— 见 §3 设计点。

## 2.5 能力形态:为什么不是 tool(2026-07-11 定)

**MCP 把每种解析包成 tool,是因为计算发生在远端**——tool 是 RPC 边界,提交任务、异步取结果,分多个 tool 是他们服务端 API 的形状。**本地解析的"计算"就是当前会话模型自己的推理**,没有远端可调:若包成 tool,tool 内部还得再起一次 LLM 调用(自套娃),平白引入第二个模型调用点、上下文割裂、流式输出丢失,还杀死"解析完接着追问"的会话体验。

所以本地线**既不是一个通用解析 tool,也不是 N 个能力 tool,而是零个新 tool**:

- 用户侧:**零新增入口,"对话即能力"**(2026-07-11 产品定案,推翻同日早先"本地预置项与 MCP chip 并列"的草案——本地/MCP 路线之争**不暴露给用户裁决**)。本地解析是 octo_insight 的默认对话行为:常驻方法论段保证用户上传材料后直述「帮我做观点解析」即触发完整流程(extract → 分析 → 落盘)。「研究工具」chip 维持 017 现状,仍是唯一显式入口——用户认知里它是「提交专业解析服务」,只要不新增本地按钮,路线之争在产品面上不存在。v1 附带收益:本地能力"软上线",评测(§7)过线前不动任何既有入口。
- 模型侧执行 = 会话内直接分析(单文档)或 spawn reader 子代理(多文档),用的工具只有取数(extract_document)和落盘(write)这两类**原语**;
- 新能力(思维导图等)= 新增一段方法论提示词,不新增 tool、不新增入口。
- **后续演进(评测过线后议,v1 不做)**:chip 菜单能力项改为路线无关——用户选「观点解析」,代码按确定性规则(token 阈值 / 格式 / 队列可用性)路由本地或 MCP,用户始终只感知能力。动既有默认路由,需产品确认 + §7 数据。

**能力感知(2026-07-11 补,回答"不做 tool 用户怎么知道本地能做什么")**:感知不靠 tool——tool 是模型的原语,用户感知能力靠模型自述,业界同构(原生能力走模型自述/产品面,外接集成才走加号/工具菜单;017 的「研究工具」chip 即集成入口,定位不变):

1. **自述真相源 = skill 索引(§2.7)**:能力以 SKILL.md 承载后,skill 机制每会话自动把可用能力的 name+description 注入 system prompt——「你能干什么」的答案就是这份索引,**不手写第二份清单**(手写清单必然与实际能力漂移)。常驻提示词只加一句引导:「用户询问你的能力时,按可用 skills 清单如实介绍本地分析能力,MCP 解析引导用户看输入框研究工具」——与 017 已有的「不要凭空描述 MCP 细节」负面约束互补。
2. ~~空态 / 输入建议~~ **挂起(2026-07-11 用户定)**:属 UI 呈现工作,且预置提示词按钮在前几版曾是 MCP 触发入口,复用该交互承载本地能力会让用户对"按钮=什么"的心智二次混乱——017 刚把触发语义收干净,不走回头路。将来若做,前提是先定清"建议按钮"与"工具菜单"的视觉/语义区分,归 UI spec,不在能力线。

工具(read/extract/write)是模型的操作原语,能力(观点解析/竞品分析)是用户的任务目标——用户可选界面只出现后者。工具调用的**过程**展示(转圈行)不隐藏,但显示名人话化,见 SPEC-INS-021 §4。

## 2.6 引用校验器(设计点 ③,v1 收尾项/可单列)

- **现状问题**:模型编造引语是**静默**的——产物里"言之凿凿"的引用没人核对,弱模型下这是最伤信任的失败模式。
- **机制**:产物 write 落盘后,代码(非模型)对每条 `「引语」` 在源文件抽取文本中做子串匹配(先按锚点段定位,失败再全文;允许空白归一化,**不做模糊语义匹配**——确定性优先):命中 → 通过;未命中 → **响亮标注**(产物内该条后加 `⚠️ 引语未在原文找到`,或产物尾部附核验报告),并把失配清单回灌模型自纠一轮(至多一轮,纠不动就带标注交付)。
- **用户感知**:报告里每条引用可信与否一目了然;差产物不再伪装成好产物。这是"响亮失败"原则在产物质量上的落点。
- **实施位**:编排归代码——挂在产物落盘后的后处理,不是 tool、不进提示词祈祷。v1 时间紧可单列小任务,但锚点(§2)必须随 v1 落,否则校验器没有地基。

## 3. 产物落盘与卡片(设计点 ①)

- 模型用 `write` 把产物写入 `insight/<sessionId>/outputs/`(文件名含能力名 + 源文件名,撞名加后缀,与 SPEC-INS-014 v2 会话隔离约定一致)。
- **待调研**:本地 write 产物如何出文件卡片 —— 现有卡片依赖当前 turn tool-call part([learning](../../learning/file-card-depends-on-current-turn-tool-call.md)),write 调用的 part 能否被 detectCard 路由;不能则 v1 先「对话内摘要 + 产物路径」,卡片接线单列小任务。
- 版本策略从 v1 就定死:**产物不可变**,修改产出新文件(`-v2` 后缀),不原地覆盖(为 ROADMAP D 二次生成铺底)。

## 5. 多文档:task 子代理 = map-reduce 的 map 步(设计点 ②)

| 方案 | 说明 | 结论 |
|---|---|---|
| **A. task 子会话按文件分治** | 每文件 spawn 一个子会话(独立上下文)做观点解析,父会话收结构化产物做跨文件综合 | **✓**:上游原语免费,天然就是 map 步;父会话只积累压缩产物,不积累原文 |
| B. 自定义拆分 pipeline | 代码层切分 / 并发 / 合并 | ✗ v1 无必须场景(见 §0),埋点数据说话 |
| C. 全部原文灌父会话 | 多文件拼接直喂 | 2–3 份小文件可行(舒适区内),更多则挤爆会话预算;作为 A 的下限兜底,模型自行判断 |

- 需新增 **`octo_insight_reader` 子代理定义**(mode: subagent):工具集 `extract_document` / `read` / `grep`,提示词 = 观点解析方法论 + §2 输出契约;产物带源文件路径与引用,父会话追问时可定点 `read` 回读原文,不全文重灌。
- 弱环节是父会话能否可靠地逐文件发 task:预置提示词模板兜底(「对 [附件] 全部文件逐一子代理解析再综合」);GLM 5 下先试模型自主编排,不行再上模板。
- ⚠️ 前置对齐(2026-07-13,SPEC-INS-021 §1 追加后):task 对**普通用户 turn 已被 turn 级 gate 默认关闭**(内部编排原语,不经用户提示词触发)。本节的多文档分治属"我们编排的 turn",落地时由构造方显式放行(buildToolGate 加参数、该 turn 下发 `task=true`);"模型自主编排"试验也在该编排 turn 内进行,不依赖模型在普通 turn 里自发起。

## 7. 评测(内网闭环)

- **评估人**:内网专业用研同学(最优评估资源),按评分表打分,不凭感觉:观点覆盖率 / 忠实性(无幻觉) / 引用准确性 / 对写报告的实际有用度,各 1–5。
- **数据集**:真实逐字稿截 20k / 40k / 80k token 三档;金标准种子向 MCP 团队要(他们的评测集 / badcase 最值钱)。
- **产出**:§6 阈值校准值;「128K 直喂质量曲线」结论回写本 spec;**文档与打分留在内网,外传仅结论数值**。
