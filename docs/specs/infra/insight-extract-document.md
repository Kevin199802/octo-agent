> ## 修订记录
>
> **2026-08-06:v2(全量落盘,工具不再丢数据 —— 反转 §4「整篇返回 + 撞通用 Truncate 兜底」)**
>
> **内网实测现象**:三四万字的 docx 抽取后正文被砍掉一半以上;一轮上传 10 个文件必失败、分两批各 5 个就正常;分批读完后让模型「基于上面 10 份文档写报告」,模型又从头一个个重读。
>
> **根因(三条,都不在解析库)**:
> 1. **50KB 是字节不是字符**。[truncate.ts](../../../packages/opencode/src/tool/truncate.ts) 的 `MAX_BYTES = 50 * 1024` 对中文 UTF-8(3 字节/字)等于 **~1.7 万汉字**,比 v1 §4 里按「≈2.5 万汉字」估的低三分之一。这层兜底是给 bash/grep 那类「输出多半是噪音、头部够用」的工具设计的,套在「全文本身就是目的」的文档抽取上语义就错了 —— 它按字节盲切,切在半句话上,且恢复路径(Read offset/limit)对无行号语义的正文很难用。
> 2. **10 vs 5 是上下文窗口的除法题**,与并发无关(工具调用是 `concurrency: "unbounded"`,没有并发闸)。每个文件即使被砍到 50KB 也是 ≈1.7 万 token,10 个 ≈17 万超窗口 → [overflow.ts](../../../packages/opencode/src/session/overflow.ts) 判定 overflow → auto compaction。
> 3. **模型重读不是理解力问题**。compaction 把旧历史压成摘要后,正文已不在模型上下文里(UI 显示的是数据库原始消息,模型看到的是重组后的上下文,**两者会分叉**)。它眼前只剩文件路径,重读是正确行为。
>
> **决定**:工具的职责是**把全文完整交付出来**,「上下文塞不塞得下」是上层的事,工具无权代为丢弃。改为 **全量落盘 + 阈值分流**(§4.1):正文一律写进 `.octo/<sessionID>/extracted/`,小文件额外内联返回全文,大文件返回元信息 + 落盘路径 + 开头预览,由模型按提示 grep/read 取用。工具自己保证永远不撞通用 Truncate 兜底。
>
> **被否掉的备选**:
> - **按 heading 层级切分 / 结构化分页**(业界 Docling、MarkItDown、unstructured.io 的路线)——起草时提出,评审否掉:真实用研素材大量是手动加粗当标题、根本没有样式层级,heading 树多半为空,白加一层结构还多一个失败面。全量备用 + 用户提示词驱动更通用。
> - **解析结果进文件管理**——讨论后否掉。SPEC-INS-014 v4 把 outputs 定义为「会话真产物库,只收真·文件产物」并特意排除中间件,理由是「无差别落盘会用对话碎片淹没产物库」;解析件与用户上传的原件一一对应、内容重复且格式更差,对用户几乎无使用价值(它是给模型看的)。故落 `extracted/`(文件管理的 `listFiles` 只认 uploads/outputs 两个 category,不列它),**一致性由「行为契约一致」保证,不靠「都在 UI 里露脸」**。
> - **子代理分治**——是「10 份文档做通读类任务」的正解(子会话独立上下文,只回传结论),但本次不做:现阶段 registry 把 `extract_document` gate 在 `agent.name === "octo_insight"`,子代理拿不到工具;且子会话的 UI 呈现另有待议。本 spec 只解决「工具自身不丢数据」。
>
> **必须认清的边界**:落盘解决的是「工具不许擅自丢数据」,**不解决「全文塞不塞得下」**。定位类任务(grep)从此完美;通读类任务(总结 3 万字)仍需分批 read 把全文捞进上下文,10 份文档同时通读照样撞窗口 —— 区别在于这时是模型/用户在已知全文位置和大小的前提下做选择,而不是工具偷偷砍掉一半。

## 0. 形态(已收敛)

- **模型按需调的 tool,不自动内联**:遇 office 文件,模型按系统提示词调 `extract_document(path)` 拿纯文本;不在上传 / 发送时 eager 解析(大文档内联撑爆上下文)。
- **入参 = 本地路径**(`insight/sources/` 下,取自 `[附件]` 清单冒号后那串):短、干净、人类可读,与 Read/Grep 收路径同构,弱模型不易改坏——**不需要** ADR-014 那种 handle 间接层(那是为长编码 S3 URL 防的)。
- **lazy 解析**:进 tool 才读盘解析;解析结果**不缓存**(同文件重复调用重复解析、覆盖写同一落盘文件,留作后续优化——v2 的落盘是「交付通道」不是缓存,复用落盘文件需要 mtime 失效判定,见 §8)。
- **顺带返回字数 / token 估算**:E 护栏(超阈值提醒)的「测量机制」寄生在本工具免费产出,不单开 spec。

## 2. 路径引用(设计点 ②)

与 INS-015 §2 的 `[附件]` 清单**同一套**,不新增机制:清单给 `文件名: 本地路径`,`extract_document` 收路径(冒号后那串)、MCP 工具收文件名(冒号前那串)。`octo-upload-inject` 插件对 `extract_document` 直接放行(INS-015 §3-1),本地路径绝不被换成 URL。

工具不限制 path 必须在 `sources/` 下——Read/Grep 本就可读全盘,限制它不构成任何安全边界,徒增"路径对但被拒"的失败面。

## 3. 支持格式与库选型

### 3.1 支持格式(SOT)

**格式取舍只看两件事:本工具解析上能做到什么程度 × 用研需求值不值得。** 上传环节(客户端入口白名单、协作团队维护的服务端白名单)是跟随项、随时可改,不构成能力约束,扩格式时按文末对齐清单同步即可。

| 扩展名 | 解析 | 说明 |
|---|---|---|
| `.docx` | ✓ | mammoth `extractRawText` |
| `.xlsx` | ✓ | exceljs 逐表逐行取显示文本 |
| `.pdf` | ✓ | unpdf 合并各页文本;**扫描件(无文本层)返回「未抽取到文本」**(OCR 见 §8) |
| `.pptx` | ✓ | jszip + slide XML 直抽,含演讲者备注(方案与局限见 §3.3) |
| `.doc` / `.xls` / `.ppt`(97-2003 旧二进制 OLE2) | ✗ | 解析质量硬短板:mammoth / exceljs / 本 pptx 方案只认 OOXML;JS 生态解析旧二进制只有冷门库(word-extractor,.doc 尚可)或已被排除的 SheetJS(.xls 唯一选项),.ppt 无可用库。占比低 + 一步「另存为」即解决 → 回灌引导转存 docx / xlsx / pdf |
| `.pages` / `.numbers` / `.key`(iWork) | ✗ | 解析能力硬短板:专有 IWA(protobuf-in-zip)格式,JS 无可靠解析库;引导从 iWork 导出 docx / xlsx / pdf |
| `.txt` / `.md` | —(不经本工具) | 路由 ① FilePart 自动内联 |
| 图片 | —(不经本工具) | 路由 ③ vision |

**对齐清单(扩格式时逐项过)**:本表 → 客户端 `ALLOWED_EXT`(insight/lib/upload.ts,选择器 accept / 校验 / 提示文案的单一事实源)→ 插件 `DOC_EXT_RE` 预筛 → MCP 上传服务端白名单(协作团队维护,随时可配合改)→ octo_insight 提示词 office 列表。落地时已同步:**pdf**(INS-015 重构时入口遗漏,本次补回)与 **pptx** 全链对齐;pptx 的服务端白名单待协作团队跟进,跟进前 pptx 走 ②(本工具读)正常、走 ④(MCP 分析)会 415 回灌。

### 3.2 库选型(设计点:先评估再定)

| 格式 | 选用 | 排除项与理由 |
|---|---|---|
| docx | **mammoth** 1.12(`extractRawText`) | 事实标准、纯 JS;officeparser(小众)、docx4js(停更) |
| pdf | **unpdf** 1.6(unjs,内嵌 serverless 版 pdf.js) | pdf-parse v1 停更有 debug 陷阱、v2 直接依赖 pdfjs-dist(worker / canvas 可选依赖对单文件 bundle 不友好);pdfjs-dist 裸用同理。unpdf 就是为「打包进 serverless / 单文件」设计的,适配 sidecar 的 Bun.build 单文件产物 |
| xlsx | **exceljs** 4.4 | SheetJS(xlsx)npm 版停在 0.18.5 且有已知 CVE(原型污染 / ReDoS),新版只发自家 CDN——URL 依赖对内网 npm 镜像不友好、装机链路多一个外部单点;@e965/xlsx 是第三方转发布,供应链信任更差。exceljs 官方 npm 有维护,读 xlsx 取显示文本(`cell.text` 统一公式结果 / 日期 / 富文本)够用 |
| pptx | **jszip** 3.10 + 自写 slide XML 直抽(~50 行) | officeparser(多格式一把抓,但会把 docx/pdf 也换成它、各格式质量都不如专门库,只为 pptx 引全家桶不值);LibreOffice 无头转换(唯一能还原视觉阅读序的路线,但要求用户机器装 LibreOffice,桌面端不可控、重)。见 §3.3 |

四库均为 **lazy dynamic import**(进 execute 才加载,Bun.build 打进 bundle 但不占 sidecar 启动路径)。

**运行时约束**:桌面端 sidecar 是 Electron `utilityProcess.fork` 的 **Node 进程(非 Bun)**——文件 IO 用 `node:fs`,不用 `Bun.*`(INS-015 已踩过坑);四库已验证「Bun.build target=node 打包 → Node 22 运行」全通。

### 3.3 pptx 方案与已知局限

**方案 = 业界标准做法**:pptx 是 zip 容器,幻灯片文字全在 `ppt/slides/slideN.xml` 的 `<a:t>` 文本节点里(叶子节点、不嵌套,正则提取即可,不需引 XML 解析器)。officeparser / python-pptx / unstructured.io 的 pptx 抽取本质都是这一套——纯解析层面没有更高级的方案,要更好只能走 LibreOffice 转换 / 商业文档智能 API(重,见 §3.2 排除项)。实现细则:按 `<a:p>` 段落聚合成行、XML 实体解码、每页输出 `# 第 N 页` 分节;**演讲者备注**经该页 rels 定位 `notesSlideM.xml`(编号与 slide 不保证一致,不能按同编号猜),以 `[备注] ` 行附于该页。

**已知局限(如实告知,不装能)**:

| 局限 | 说明 |
|---|---|
| **文本框顺序 ≠ 视觉阅读序** | XML 里 shape 按插入序存储。规矩的模板页(标题 + 正文占位符)顺序基本正确;设计感强、文本框自由摆放的页面会乱序。对「给模型读内容提观点」影响有限(LLM 对段落袋容忍度高),对「按页复原报告结构」类任务不可靠 |
| SmartArt 文字不收 | 存在单独的 diagram XML(`ppt/diagrams/`),需 rels 级联解析,v1 不做 |
| 内嵌图表数据不收 | 图表数据在内嵌 xlsx 部件里,v1 不做 |
| 表格文字**能收** | 表格(`<a:tbl>`)单元格文字同样是 `<a:t>`,随段落自然带出,但丢行列结构(一格一行) |
| 图片上的文字无 | OCR 范畴,见 §8 |

## 4. 输出契约(v2)

### 4.1 全量落盘 + 阈值分流

抽取成功(`chars > 0`)时,正文**一律**先写进本会话的解析件目录,再按体积决定要不要同时内联返回:

| 分支 | 判据(对**折行后**的正文) | 返回 |
|---|---|---|
| **内联** | 行数与字节都 ≤ 内联阈值 | 元信息 + 落盘路径 + **全文** |
| **仅落盘** | 任一维度超阈值 | 元信息 + 落盘路径 + **开头预览(2000 字)** + 取用指引 |

**行为一致性**:两个分支**都落盘**。小文件只是额外多给一份内联全文(「一式两份」),不存在「小文件没有落盘文件」这种分叉。

**内联阈值 = 通用 Truncate 限额的 80%**(`Truncate.limits()` 读的是 config `tool_output`,可被用户覆盖,故取运行时值而非硬编码)。留 20% 余量是为了容纳首部元信息 / 指引行 —— **工具必须保证自己永远不触发 [tool.ts](../../../packages/opencode/src/tool/tool.ts) 那层 Truncate 兜底**,一旦触发就意味着又一次盲切。

**为什么阈值判据用折行后的正文**:落盘的和内联的必须是同一份文本,否则「模型读到的」和「盘上的」会分叉 —— 那是比截断更难查的 bug。

### 4.2 落盘位置与命名

- 目录:`<projectDir>/.octo/<sessionID>/extracted/`(SPEC-INS-014 布局下 `uploads/`、`outputs/` 的兄弟;**不进文件管理**,理由见修订记录)。惰性创建。
- 文件名:`<源文件主名>.md`。
- **为什么 `.md` 而不是 `.txt`**:抽取输出本来就是 markdown —— xlsx 走 `# 工作表:<名>`、pptx 走 `# 第 N 页`;且本仓 md 有应用内预览 / 编辑器渲染,txt 没有。代价是 docx 正文里的 `#`、`*` 会被误渲染成标记,可接受。
- **撞名**:文件首行写 `<!-- source: <源文件绝对路径> | chars: N | extracted: <ISO 时间> -->`。落盘前若同名文件已存在且首行 source **不是**本次源路径,则退到 `<主名>-2.md`、`-3.md`…… 直到不冲突。
  - 为什么需要:`/a/报告.docx` 与 `/b/报告.docx` 抽成同一个 `报告.md` 会**静默串数据** —— 模型拿着前者的路径 read 到后者的内容,这在一份「不丢数据」的 spec 里不可接受。
  - 为什么大多数时候走不到:上传落盘时 desktop 侧 `collisionFreePath` 已保证会话 `uploads/` 内文件名唯一,同名只可能来自会话外的直接路径引用。

### 4.3 软折行(强制)

落盘正文按 **≤500 字符/行** 折行(在 300–500 区间内优先切在句末标点 `。！？；.!?;` 之后,找不到则 500 处硬切;≤500 的行原样保留)。

两个理由,**第一个是硬性的**:

1. **`read` 的 `MAX_LINE_LENGTH = 2000` 会砍掉超长行的尾巴,且没有任何续读手段 —— 那部分内容永久丢失**([read.ts](../../../packages/opencode/src/tool/read.ts))。而 `mammoth.extractRawText` 的输出正是「一个段落一行」,访谈稿里一段几千字很常见。不折行的话,落盘等于白落。
2. **grep 命中时返回整行**,行太长会把大段无关内容灌进上下文,grep 的定位价值就废了。500 字符对中文约两三句话,是合适的检索粒度。

折行是纯机械处理,不做任何结构理解(不识别 heading、不重排段落)。

### 4.4 返回文案

内联分支:

```
《访谈稿-张三.docx》抽取完成:共 12,345 字(非空白字符),估算约 9,800 tokens。全文已保存到:<绝对路径>
---
<正文全文>
```

仅落盘分支:

```
《访谈稿-张三.docx》抽取完成:共 35,120 字(非空白字符),估算约 28,000 tokens。
正文过长,未直接返回;全文已保存到:<绝对路径>
需要定位具体内容,用 grep 搜关键词;需要通读,用 read 按 offset/limit 分段读(单次上限 2000 行 / 50KB)。
以下为开头预览:
---
<前 2000 字>
```

- **首行仍是测量结果**:即便将来又撞上什么 head 方向的截断,字数 / token 估算永远可见。
- 预览取 2000 字(约 6KB),给弱模型一个内容锚点 —— 只给路径不给内容,它容易拿到路径就开始编。
- token 估算沿用业界粗算(CJK 每字 ≈1 token、其余 ≈4 字符/token),只求量级正确。
- `metadata`:`{ path, format, chars, tokenEstimate, savedPath?, inlined, pages?, sheets?, slides? }`。

### 4.5 各格式正文形态(不变)

docx = 段落文本(**表格降为按单元格分段、样式图片丢弃**);pdf = 合并各页文本(**扫描件无文本层则空**);xlsx = 每工作表 `# 工作表:<名>` + TSV 行;pptx = 每页 `# 第 N 页` + 段落行 + `[备注] ` 行(局限见 §3.3)。

## 5. 失败语义(全部以正常输出回灌,不抛错)

| 情形 | 回灌文案要点 | metadata.error |
|---|---|---|
| 文件不存在 | 指引「路径取自 `[附件]` 清单冒号后那串」 | `not-found` |
| 不支持格式(.doc/.xls/.ppt/iWork/…) | 列支持格式 + 引导「转存为 docx / xlsx / pdf 后重新上传」(转存一步即解决,比任何兜底都直接) | `unsupported` |
| 解析失败(损坏 / 加密) | 带解析器原始错误信息 + 建议改走 MCP | `parse-error` |
| 解析成功但无文本(扫描件) | 说明可能是扫描件 / 纯图片文档 + 建议改走 MCP | —(`chars: 0`) |
| **落盘失败(v2:磁盘满 / 权限 / 目录建不出)** | **降级为整篇返回**(退回 v1 行为,由通用 Truncate 兜底),文案里说明「全文未能保存」 | —(`savedPath` 缺省) |

**落盘失败为什么降级而不是报错**:写盘是交付通道的优化,不是解析能力本身。盘写不了就退回 v1 那条路(内联 + 兜底截断),用户至少还能拿到前半篇 —— 让整个工具因为写不了盘而失败是把小故障放大成功能不可用。

选「输出文本」而非「抛错」:两者都会回灌模型,但文本可控措辞、不在 UI 里渲染成红色工具失败;与 stub 时期语义一致。解析失败 / 无文本给 **MCP 兜底指引**(MCP 侧有自己的解析管线,可能读得动);不支持格式给**转存指引**。

## 7. 验证

单测(`packages/opencode/test/tool/extract_document.test.ts`,fixtures 为手搓最小 docx/xlsx/pdf/pptx,独立于被测库):docx 中英正文 + 首行测量、pdf 文本 + 页数、xlsx 工作表 TSV、pptx 分页 + 备注 + 实体解码、不存在 / 不支持 / 损坏三失败路径,7/7 通过;`tsgo --noEmit` 干净;四库 Bun.build→Node 22 冒烟通过。

**v2 新增单测**(同一文件):
- 小文件 → 内联返回全文 **且** `extracted/` 下有落盘文件(一式两份,不是二选一)。
- 大文件(> 内联阈值)→ 返回不含全文、含落盘路径与 2000 字预览;落盘文件内容 = 完整正文。
- 折行 → 落盘文件**每一行都 ≤500 字符**(用一段 5000 字无标点长文 + 一段有句号的长文各验一次:后者切点应落在句末标点后)。
- 撞名 → 两个不同源路径、同主名的文件先后抽取,产出 `x.md` 与 `x-2.md`,各自首行 source 指向正确源路径,内容不互相覆盖。
- 落盘失败 → mock 写盘抛错,断言降级为整篇返回且输出里说明未保存(不抛错、不丢功能)。

**体积探针(2026-08-06,一次性)**——回答「是不是多大的文件都至少能落盘」。**这不是回归用例,也不是验收标准**:耗时和内存随设备而变(下表出自一台开发机的纯文本直读路径),换台机器数字就不同,做成常驻断言只会得到一个随机失败的测试。它的用途是**定出量级和外推法则**,之后按法则预估即可,不必重复跑。

| 源文件 | 字数 | 落盘 | 耗时 | RSS 增量 |
|---|---|---|---|---|
| 1.0 MB | 36.7 万 | ✓ 1.0 MB | 229 ms | 48 MB |
| 10.2 MB | 367 万 | ✓ 10.2 MB | 118 ms | 203 MB |
| 50.9 MB | 1838 万 | ✓ 50.9 MB | 487 ms | 873 MB |
| 101.8 MB | 3675 万 | ✓ 101.9 MB | 1820 ms | **1745 MB** |

**外推法则(比上面的绝对数字更该记住的东西)**:

> **峰值内存 ≈ 源文件大小 × 17**(整篇 readFile + 整篇转 JS 字符串 + 折行中间态,三份都在内存里)。
> 换算:能否处理一份 N MB 的文档,取决于**该设备**给 sidecar 的可用堆是否 > 17N MB。

比例是架构决定的(「整篇进内存」),因此可跨设备外推;上表的绝对值不能。

结论与边界:

- **客户端上传上限就是 100MB**(`MAX_UPLOAD_SIZE`,insight/lib/upload.ts),按上述法则约需 1.7GB 可用堆——开发机上通过。**低配设备(或 sidecar 堆被限制时)可能在更小的文件上就触顶**,这是设备相关的,不是代码里能保证的常数。
- 触顶的表现是 **sidecar 进程崩溃,不是优雅的 `parse-error`**(内存耗尽发生在解析库内部,catch 不住)。内网若出现「传大文件后会话直接断」,先查这条。要根治只能改流式(读一段折一段写一段),见 §8。
- 回灌长度恒定在 ~2.3KB(预览截断生效),与源文件大小无关——这条是确定性的,有单测覆盖。
- 上表测的是 **txt 直读**路径。docx / pdf / xlsx 还要叠加解析库自身开销(mammoth / unpdf 都是整篇进内存),同体积下更早触顶;这类失败落在 `parse-error` 分支,有兜底文案、不崩。
- **落盘 ≠ 模型读得完**:100MB 的落盘件模型要 read 约 2000 次才能通读,实际不可行(grep 定位仍然有效)。「不丢数据」和「读得动」是两件事,后者见修订记录的「已知边界」。

内网端到端(替代 INS-015 §8-2 的 stub 预期):

1. 选 docx 让模型读 → 无 S3 上传、模型调 `extract_document(path)` 拿到正文并能作答。
2. **三四万字 docx** → 首行字数与真实字数一致(不再腰斩);`extracted/` 下有同名 md;模型能按提示 grep 命中具体内容、read 分段能读到**文末**(核对最后一段与原文一致)。
3. **一轮 10 个文件** → 全部抽取成功、每份都有落盘件(通读类任务仍可能撞上下文窗口,那是已知边界)。
4. **体积上限(在真实内网设备上跑一次即可,不必纳入每轮回归)**:传一个接近上传上限(80–100MB)的大文件 → 仍能落盘、回灌只有预览、sidecar 不崩。**这一条测的是「那台设备的堆够不够」,不是代码行为**——若崩了,说明该设备触到了上面的外推法则,记录设备内存与文件大小即可,不必反复试。
5. **落盘件可读性**:对上一条的落盘件跑 grep 关键词 → 命中的是折行后的段落(≤500 字符),不是整篇糊成一行。

## 8. 不做 / 后续

- 解析结果缓存(源文件 mtime > 落盘件 mtime 才重解析)——v2 落盘后这条几乎是免费的,但它引入新的失效面(源文件被改、落盘件被用户删),且 v2 的目标是「不丢数据」不是「省解析」,故仍不做,留待重复抽取真的成为瓶颈时再立。
- 按节 / 页码范围抽取、目录感知、按 heading 结构化分页——**v2 明确否掉**(修订记录「被否掉的备选」),真实用研素材普遍无样式层级;有真实需求再议。
- **子代理分治读文档**——「10 份文档做通读类任务」的正解,但需先解开 registry 对 `extract_document` 的 `octo_insight` gate,且子会话 UI 呈现另有待议,独立立项。**其价值是上下文隔离(读完就扔、只回传结论),不是并发**——内网模型并发能力一般,串行跑子代理同样能把父上下文从十几万 token 压到几千。
- **流式抽取(读一段→折一段→写一段)**——现在是「整篇进内存」,内存放大约 17 倍(§7 实测),100MB 时 RSS 涨 1.7GB。当前上传上限 100MB 尚在射程内,故不做;若上传上限放宽、或内网出现 sidecar 因大文件崩溃,这是唯一的解法。
- legacy 旧二进制(.doc/.xls/.ppt)、iWork——引导转存(§3.1);.doc 若真实需求高可评估 word-extractor 单独加。
- OCR(扫描件 pdf / 图片上文字)——tesseract.js 可行但要带语言包(中文 10MB+)、慢、准确率一般,独立决策、不捆在本 spec。
- pptx 视觉阅读序还原、SmartArt / 内嵌图表数据——见 §3.3 局限;要做只有 LibreOffice 转换路线,重,待真实需求。
- 提示词 / 白名单 / 清单格式改动——本次仅追加格式项(office 列表加 pptx、入口白名单加 pdf/pptx),机制零改动(INS-015 已就位)。
