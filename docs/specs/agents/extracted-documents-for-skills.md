# 文档解析结果 — skill 作者须知

- **面向**：写 skill（SKILL.md）和随 skill 分发脚本的人
- **一句话**：**skill 不解析文档，也不猜解析结果放在哪。** 宿主已经把 docx / pdf / xlsx / pptx 解析成纯文本落了盘，你要做的只是**接住模型递过来的路径**。
- **相关**：[产物落盘 — skill 作者须知](artifact-output-for-skills.md)（同一套「不点名目录」的精神）、[`question` 工具 — skill 作者须知](question-tool-for-skills.md)（同类对外文档）、[SPEC-INS-016](../infra/insight-extract-document.md)（宿主侧机制）

---

## 0. 宿主替你做了什么

用户上传的文档，模型会用宿主内置的 `extract_document` 工具解析成纯文本，**并且一定会落盘**（不管文档多大）。工具的返回里带着这份纯文本的绝对路径。

所以在你的 skill 跑起来之前，材料通常**已经是一份现成的 md 文件**了。

这带来两个直接后果，都在下面的规则里：

1. skill 不需要（也不应该）自己解析 office 文档；
2. skill 不需要（也不应该）知道解析结果的目录长什么样。

---

## 1. 四条规则

### 规则 1：不要自己解析文档

不要在 skill 脚本里调 `python-docx`、`pandoc`、`textract`、`unzip` 拆 OOXML，也不要让模型去 `read` 一个 `.docx`（二进制，read 会直接报错）。

```diff
- 用 python-docx 读取每个 .docx，提取全部段落文本。
- pandoc -f docx -t plain "$f" > "$f.txt"
+ 材料已由宿主解析为纯文本。使用上一步 extract_document 返回的文件路径。
```

理由不只是重复劳动：宿主那套解析是**统一入口**，格式支持、失败语义、字数统计、落盘位置都在一处维护。skill 自己解析出来的东西和它对不上，用户会看到两套互相矛盾的字数和内容。

而且 skill 脚本跑在**桌面端的 sidecar（Node 进程）**里，不保证有 python、pandoc 或任何外部二进制。

### 规则 2：路径当参数接，不要在 skill 里拼

解析结果的落点是宿主的内部布局，**会随版本改**。skill 里写死目录，改布局那天就静默失效。

```diff
- 遍历 .octo/<sessionId>/extracted/ 下的所有 md 文件。
- for f in ../extracted/*.md; do ...
+ 对用户提供的每份材料，使用其解析结果路径（由 extract_document 返回）。
+ 脚本接受一个或多个文件路径作为参数：analyze.sh <解析结果路径>...
```

模型手上有这些路径（工具返回里就写着「全文已保存到：…」），把它写成脚本参数即可。

**需要遍历「这次会话的所有材料」时**：让模型用 `glob` / `grep` 去找（宿主已经把搜索基准设成会话根，覆盖得到），把结果作为参数传进来——仍然不要在 skill 文本里出现具体目录。

### 规则 3：不要假设「一行 = 一段」

**这是最容易踩的坑。** 落盘的纯文本做过**软折行：每行不超过 500 字符**，长段落会被切成多行。

```diff
- 逐行读取，每一行是一个发言段落。
- awk 'NR==1{print "第一段: "$0}'
+ 按空行分段，或整篇读入后按语义切分；不要把「行」当「段」。
```

为什么要折行（这不是随便定的）：宿主的 `read` 工具对**超过 2000 字符的行会直接砍掉尾部且无法续读**，不折行的话超长段落会永久丢内容；同时 `grep` 命中时返回整行，行太长会把大段无关内容灌进上下文。

还有两条形态约定：

- **首行是一条 HTML 注释**（`<!-- source: … -->`），记录来源文件与字数。按行处理时记得跳过它。
- 文件是 **`.md`**，但正文是文档的**纯文本**：docx 的段落、xlsx 的 `# 工作表:<名>` + TSV 行、pptx 的 `# 第 N 页` + `[备注] ` 行。里面出现的 `#`、`*` 可能只是正文里的普通字符，不要当 markdown 结构解析。

### 规则 4：容错，不要假设文件一定在

绝大多数情况下解析结果都在，但有几种情况它不在：磁盘写入失败（宿主会降级成直接把正文交给模型）、用户手工删了、或者这份材料压根没经过解析（比如扫描件 PDF 抽不出文本层）。

```diff
- cat "$1" | 分析
+ 若给定路径不存在或为空，向用户说明这份材料未能解析，并继续处理其余材料。
```

一份材料读不到，应当跳过并说明，而不是整个 skill 失败。

---

## 2. 不要做的两件事

**不要把解析结果当作交付产物。** 它是给模型看的中间件，宿主**有意**不把它放进文件管理面板——用户手上有原件，格式还更完整。skill 要交付的是分析结论，产物落盘规则见[产物落盘须知](artifact-output-for-skills.md)。

**不要为了「保险」重新抽取一遍。** 同一份文档解析多次，结果一样，只是更慢。如果之前抽取的正文已经不在模型的上下文里（长对话会发生），正确做法是**用那个落盘路径 grep / read**，而不是重新调 `extract_document`。

## 3. 自查清单

发布 skill 前逐条过：

- [ ] 没有调用任何外部解析工具（python-docx / pandoc / textract / unzip）
- [ ] 没有出现 `.octo`、`extracted`、`../extracted` 之类的具体目录
- [ ] 脚本通过**参数**接收文件路径，不自己去目录里捞
- [ ] 没有「逐行 = 逐段」的假设；跳过了首行注释
- [ ] 单份材料缺失时能跳过并说明，不整体失败
- [ ] 没有把解析结果本身当成交付物写进产物目录
