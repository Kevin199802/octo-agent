# `question` 工具 — skill 作者须知

- **面向**：写 skill（SKILL.md）和写 agent 提示词的人
- **一句话**：让模型在需要时向用户提问、拿到选择后继续。skill 里用自然语言点名 `question` 即可，不需要写调用参数。
- **相关**：[skill-system.md](skill-system.md)、[mcp-contract.md](mcp-contract.md)（对照：那份为什么是契约，本份为什么不是）

---

## 0. 这份文档是什么 / 不是什么

**不是** `question` 的出入参契约，**也不会**列参数表。

原因不是偷懒，是这类文档天然会漂移且没人用：

| | MCP（有 `mcp-contract.md`） | `question`（本文档） |
|---|---|---|
| 边界性质 | **跨团队线缆边界**——UXR 团队按契约实现 server，我们消费 | 本仓内置工具，没有第二个实现方 |
| 契约给谁看 | **人**：对方团队照着写代码 | **模型**：schema 由 `Tool.define` 转成 JSON Schema 自动进上下文 |
| 不写会怎样 | 两边实现对不上，联调爆炸 | 不会怎样，模型本来就读得到 |

更根本的一点：**skill 作者不调用工具，模型才调用**。

SKILL.md 注入的是给模型看的自然语言指令；决定调不调、`multiple` 填 true 还是 false、选项怎么拆，全是模型在读 schema 后自己定的。skill 作者从头到尾不会写出 `question({questions:[...]})` 这种东西——所以一份参数表对他们没有用武之地。

手抄 schema 还容易抄错。真实例子：`QuestionTool` 的参数类型是 `Question.Prompt`，只有 `question / header / options / multiple` 四个字段；`custom`（是否允许自定义答案）只存在于 `Question.Info` 上，**模型根本设不了**。人肉写文档几乎必然把 `custom` 抄进去，然后 skill 作者对着一个不存在的旋钮写指引。

> **真相源**：参数看 `packages/opencode/src/question/index.ts`（`Prompt` / `Option`），工具描述看 `packages/opencode/src/tool/question.ts` + `question.txt`。本文档只写 **schema 表达不了的东西**。

## 1. 前提：工具默认是关的（最容易踩的坑）

`packages/opencode/src/agent/agent.ts` 的全局 `defaults` 里写着：

```ts
question: "deny",
```

**对所有 agent 默认关闭**。agent 的权限配置里没有显式 `question: "allow"`，这个工具就不在模型的工具列表里——现象是模型回**「我并没有名为 question 的工具」**，而不是报错或卡住。

目前显式放开的：`plan`、`octo_insight`。其他 agent（design / studio / pattern 等）要用，得各自在 `agent.ts` 里放开。

自查命令：

```bash
bun run --cwd packages/opencode --conditions=browser src/index.ts debug agent <agent 名>
```

看输出末尾 `tools` 映射里 `question` 是 `true` 还是 `false`。

**还有一层**：工具可用 ≠ 用户能答。承载答题 UI 的页面必须实现了答题组件，否则服务端会阻塞等答复、会话永久挂起。目前 insight / chat / make / design 有；其余页面没有。

## 2. 在 skill 里怎么写

写**意图和时机**，不写调用语法：

```markdown
## 开始分析前

如果用户没有说明要查哪个知识库，用 question 工具问用户选一个，
选项取「产品知识库 / 技术文档库 / 客服问答库」，单选。
不要自己猜，也不要默认选第一个。
```

要点：

- **点名工具名 `question`** —— 别写"问一下用户"，弱模型（内网 GLM）不一定能把它映射到工具调用
- **给明确触发条件**（"如果用户没说明…"），别只说"必要时可以问"
- **分支若依赖答案，就把选项文本写死在 skill 里**（见下一节）

---

## 3. 模型拿得到答案吗？拿得到，但形态要注意

**拿得到。** 答案作为工具返回结果进入模型上下文，模型可以据此走分支。

模型实际看到的字符串（`tool/question.ts` 构造）：

```
User has answered your questions: "本次分析要聚焦哪个维度?"="评估打分", "需要哪些产物?"="Markdown 报告, Excel 明细表". You can now continue with the user's answers in mind.
```

四个关键性质：

1. **按问题原文回填**，不是按 id 或序号
2. **答案是选项的 `label` 文本**，不是索引、不是 id
3. **多选用 `", "` 拼接**成一个字符串
4. **没作答的题**回填字面量 `Unanswered`

> ⚠️ `metadata.answers` 里那份结构化数组**只给 UI 用，不进模型上下文**。模型能依据的只有上面那段自然语言。

### 由此而来的写法约束

- **分支要稳，就把选项 label 写进 skill**，让模型照抄，别让它每次自由发挥措辞——否则这次生成"评估打分"、下次"评分评估"，你的分支条件就对不上了
- **label 里别用逗号** —— 多选是用 `", "` 拼的，label 内含逗号会和分隔符混淆，模型无法区分"一个含逗号的答案"和"两个答案"
- **别把 label 叫 `Unanswered`** —— 和"未作答"哨兵值撞车
- **label 之间语义要互斥**，别出现"关键发现"和"核心发现"这种模型自己都分不清的组合

### 确定性边界（重要）

分支是**模型读文本后自行判断**的，不是代码层的确定性路由。也就是说：

> `question` 适合让模型"知道用户想要什么"，**不适合**用来实现"必须精确命中某个分支否则出错"的流程控制。

如果某段逻辑错了会导致产物错误或数据写错，别把它挂在模型对答案文本的解读上——那属于需要确定性机制的场景，应当在代码层用显式入口（如按钮 / chip 触发的参数）来做，而不是靠模型转述。分支越少、选项越互斥，弱模型越不容易翻车。

## 4. 用户忽略了怎么办

用户点「忽略」（或按 Esc）后：

- **一次性跳过本轮全部问题**——不是只跳当前这一题，也拿不到"已经选了一半"的部分答案
- 对话区显示一行「问题已忽略」小字
- **对话不阻塞**，模型继续往下走

所以 skill 里要把这条分支显式写清，别让模型自己发挥：

```markdown
如果用户忽略了这个问题，就按「关键发现」这个默认维度继续，并在回答开头说明你用了默认值。
```

反过来说：**别把"必须拿到答案"当成前提**。任何一次 `question` 都可能一个答案都拿不到，skill 得有兜底路径。

## 5. UI 侧的软约束

schema 不限制，但违反了界面会难看（各页面 dock 渲染口径）：

| 项 | 建议 | 原因 |
|---|---|---|
| `header` | 短标签，几个字 | 上游 schema 注释写 max 30 字符 |
| `option.label` | 1–5 个词 | 长了虽然能整行换行不截断，但可读性差 |
| `option.description` | 一句话 | 同上 |
| 选项个数 | ≤ 6 | 超出后选项区自身滚动，用户要滚才能看全 |
| 问题个数 | ≤ 3 | 分页答题，问多了用户容易中途放弃 |

> insight 的答题 UI 已确保长文本**整行铺开、换行不截断**（不做词组胶囊），所以长 label 不会撑破界面——但"不会崩"不等于"好用"。

---

## 6. 什么时候别用

- **答案是开放式的**（"你想分析什么？"）→ 直接在对话里问，别硬套选项
- **选项要动态枚举且可能很多**（列出全部 200 个知识库）→ 该做成 UI 入口（chip / 面板），不是问答
- **只是想确认一下**（"要继续吗？"）→ 多数情况是多余的往返，直接做
- **需要确定性路由** → 见 §3 确定性边界
