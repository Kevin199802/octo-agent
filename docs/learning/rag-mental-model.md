# RAG 心智模型:一堆结构化数据怎么变成"带出处的问答"

> 写给"对 RAG 没什么感知"的读者(2026-06-10)。读完你应该能回答:内网那个接口返回一堆 chunk,**怎么就变成了带引用下标 [1][2]、末尾还有参考文件列表的问答效果**?这是业界标准做法吗?
>
> 配套阅读:[rag-chat-integration.md](rag-chat-integration.md)(怎么把它接进 chat 的架构选型)。本篇只讲**原理与呈现**,不讲接法。

---

## 1. 一句话:RAG = 检索 + 生成,两段拼起来

LLM 自己脑子里没有你们内网文档的知识,直接问只会编。RAG 的办法是**先查资料、再让它照着资料answer**:

```
用户问题
   │
   ├─①检索(Retrieval):拿问题去知识库,捞回最相关的几段原文(chunk)
   │        ↑ 内网那个 getKnowledgeVector 干的就是这一段
   │
   └─②生成(Generation):把"问题 + 这几段原文"一起喂给 LLM,
            让它【只依据这些原文】写一段自然语言答案
            ↑ 这一段是我方 LLM 干(因为接口返回的 answer 字段是空的)
```

**关键认知**:接口返回的不是"答案",是"**素材**"。答案是 LLM 现场基于素材写出来的。所谓"RAG 效果"——答得准、有出处、不瞎编——本质是**第②段的 prompt 怎么写**决定的,不是接口直接给的。

---

## 2. "一堆结构化数据"是怎么喂给 LLM 的

接口返回里真正有用的是一条条 **chunk**(文档切块),每条带:

- `TOPIC_CONTENT`:这段原文内容(中文 markdown)
- `_score`:相关性分(越高越相关)
- 以及它所属文档的 `url` / 分类 / 作者等(出处信息)

我们不会把几千行原始 JSON 丢给模型,而是**整形成"编号清单"**再喂:

```
以下是检索到的资料,请只依据它们回答,并在引用处标注来源编号:

[1] (来自《用户酬金申请流程》) 普通用户酬金申请流程分为三步:首先按渗透率分类……
[2] (来自《用户酬金申请流程》) 邮件需包含调研名称、用户信息、调研方式……
[3] (来自《访谈管理规范》) 审批主体为业务归属的四级部门主管……

用户问题:如何申请访谈酬金?
```

LLM 读完,写出:

> 申请访谈酬金分三步:先按用户渗透率(高/低)分类 [1],再通过邮件提交申请,邮件需包含调研名称、用户信息与方式 [2],最后由四级部门主管审批 [3]。

—— 这就是"RAG 效果"。**注意 [1][2][3] 不是接口给的,是我们给素材编了号、并在 prompt 里要求模型"引用处标号",模型照做的结果。**

---

## 3. 引用下标 [1][2] 与末尾参考列表,是怎么来的

这是两层,都建立在"每条 chunk 有身份、能追溯到源文档"之上:

| 呈现元素 | 怎么产生 | 依赖的数据 |
|---|---|---|
| **行内引用下标 [1]** | prompt 给 chunk 编号 + 指令"论断旁标来源号",LLM 生成时标 | chunk 的"编号"(我们排序后赋的)|
| **末尾参考文件列表** | 收集被引用到的 chunk,按所属文档**去重**,列出标题 + 链接 | 每条 chunk 的父文档 `url` / 标题 / 分类 |

流程:
1. 检索 → 得到 chunk 列表,排序后编号 [1..N](编号 = chunk 在清单里的位置)。
2. 编号清单喂 LLM,LLM 答案里带 [n]。
3. 客户端解析答案里出现过的 [n] → 映射回 chunk → 取其父文档 `url`/标题 → 按文档去重 → 渲染成"参考文件"列表(点开跳原文)。

**所以内网那个老 web 应用的下标+参考列表,就是这么实现的**:同一份检索数据,一份用来喂模型(带编号)、一份用来渲染来源卡片。

## 4. 现有数据结构支持这些吗?——支持,但有一个坑

| 呈现需要 | 接口字段 | 是否支持 |
|---|---|---|
| 引用片段内容 | `chunk_list[].TOPIC_CONTENT` | ✓ |
| 相关性排序/编号 | `chunk_list[]._score`(数字) | ✓ |
| 跳转原文链接 | `data[].data[].url` | ✓ |
| 文档分类标签 | `ClassificationL1..L5` | ✓ |
| 作者 | `author` | ✓ |
| 高亮摘要(列表里给个 preview) | `highlight.markdown_content[]` | ✓ |
| 图/页码 | `TOPIC_FEATURE.IMAGE_URL_LIST` / `PAGE_START_END` | ✓ |
| **文档标题** | `TOPIC_TITLE` | ⚠️ **坑**:实测它≈整段正文,**不是干净标题** |

**唯一的坑**:`TOPIC_TITLE` 不能直接当参考列表的标题用(它塞的是正文)。替代:用 `ClassificationL*` 拼、用 `DOC_ID`、或取 `markdown_content` 首行做标题。其余出处信息都齐全,**做下标+参考列表完全没问题**。

## 5. 业界一般就是这么做的吗?

**是的,这就是 RAG 的标准两层结构**,你直觉里的"调一个服务端封装接口 + 结合 LLM 输出"正是主流:

```
[检索服务] ──chunks──> [LLM 生成] ──> 带引用的答案 + 来源列表
 (向量/ES 检索,           (按素材作答、标引用)
  内网这个接口就是它)
```

- **Perplexity / Glean / Bing Copilot / 各家企业知识库**都是这个骨架:一个检索后端 + 一个会"照着资料带引用作答"的 LLM。
- **两个常见变体**(区别只在"生成在哪做"):
  1. **检索服务只检索**,生成交给调用方的 LLM —— **就是我们这种**(接口 `answer` 为空)。最灵活,能换模型、控制 prompt。
  2. 检索服务**连生成一起做**,直接返回成品答案 —— 调用方只展示。省事但不可控。
- 引用与参考列表,**业界也都是在"生成 + 客户端渲染"这层做的**,不是检索接口直接吐 HTML。和上面第 3 节完全一致。

所以我们的方向没有偏:**复用内网检索接口 + 我方 LLM 生成带引用的答案**,是标准姿势。

## 6. 端到端走一遍(用我们的接口)

```
用户在 chat 问"如何申请访谈酬金"
   │
   ▼ LLM 判断该查库 → 调 knowledge_search("如何申请访谈酬金")
工具 POST getKnowledgeVector { account, context }
   │
   ▼ 返回 data[].data[].chunk_list[](一堆带 _score 的 TOPIC_CONTENT)
工具整形:扁平化 → 按 _score 降序 → 取 top-k → 编号清单(保留各 chunk 的 url/标题备用)
   │
   ▼ LLM 读编号清单,写答案 + 行内 [n]
客户端:解析 [n] → 映射父文档 → 去重 → 渲染参考文件列表
```

## 7. 和 chat V1 的关系:呈现是"同一份数据的升级"

V1 为了快,先只做**内联自然语言答案**(不强求下标/参考列表)。但要认识到:**下标 [n] 和参考列表并不需要新数据,就是同一份检索结果换个呈现**。所以路线是:

- **V1**:检索 → 编号清单喂模型 → 内联答案(prompt 可以已经要求带 [n],只是先不渲染参考卡片)。
- **迭代**:客户端解析 [n] → 渲染行内角标 + 末尾参考文件列表(复用 insight 卡片基建)。

前提是**检索整形层从一开始就保留每条 chunk 的父文档 url/标题/分类**(别在第一步就丢),这样升级呈现时零返工——这条已写进 [rag-chat-integration.md](rag-chat-integration.md) §8 扩展阶梯与 spec。
