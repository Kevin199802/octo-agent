# ADR-013: 长任务进度查询策略 — 卡片刷新按钮(LLM 触发)

## 状态

已采纳（2026-05-20）

---

## 背景

UXR 内网 MCP 服务的业务工具（`key_findings` / `run_guide_analysis` / `run_usability_analysis` / `mindmap`）属于长任务，调用即提交、返回 task_id，实际分析时长可达 **30 分钟**（[mcp-contract.md](../specs/agents/mcp-contract.md) 已规范化这一异步形态）。

需要决定：用户如何看到任务进度，以及任务完成后结果如何呈现。

设计师反馈"用户主动查询进度"体验差，希望"自动展示进度"。需要在工期、用户量（几十人）、契约形态等约束下务实落地。

---

## 业界对照 — 时长决定形态

agent 对话产品的"任务时长"和"标准形态"严格相关：

| 时长 | 业界标准形态 | 代表产品 |
|---|---|---|
| < 3s | 直接返回，无 loading | 简单问答 |
| 3-10s | spinner + loading 文案 | ChatGPT 常规问答 |
| 10s-1min | SSE 流式 token 输出 + 状态展示 | Claude 长回答 / GPT-4 普通推理 |
| 1-3min | SSE 流式 + 中间步骤（思维链 / 工具调用）逐条展示 | Claude Code / Cursor / GPT-4 deep thinking |
| 3-10min | SSE 流式 + 显式"长任务"标识，**仍在同一 turn** | OpenAI Codex 完整任务 / Cursor Background Agent 早期 |
| 10min+ | **必须脱离对话流**，进入"任务管理"形态 | Devin / 批处理产品（OpenAI Batch API）|

### 关键阈值：5 分钟

**5 分钟是 agent 对话流形态的舒适上限**：
- 5 分钟内，SSE 长连接被网关 timeout 杀掉的风险可控（nginx 默认 60s，可调到 300s）
- 5 分钟内，用户对"还在做"的认知不会衰减
- 5 分钟内，中间步骤展示能让用户感觉"它在工作"，不会怀疑卡死

业界没有"agent 对话 + 30 分钟同步任务"这种组合。本产品当前在一个真空地带，没有可直接照搬的标配。

---

## 最佳方案：SSE 流式（业界 agent 标准形态）

### 形态

MCP 协议基于 Streamable HTTP，**原生支持 SSE**。完整形态：

```
客户端调 key_findings(...)
  │
  ├──HTTP POST + SSE──►  UXR /mcp
  │                       ├─ event 1: "已收到，开始解析文档..."
  │                       ├─ event 2..N: "已完成 30%..." / "聚合中..."
  │                       └─ final: text part + resource_link
  │                       连接关闭
  ▼
对话流流式渲染（与 LLM 输出 token 同构）
```

**SSE 的工作原理**：服务端持续 write 数据，客户端 `onmessage` 接收，直到完成时关闭连接。数据流本身就证明连接活着，通常不需要心跳。服务端若有较长"无数据间隔"，可发送 `: keepalive\n\n` 注释防止网关 timeout。客户端没有 polling，只有事件监听，与 LLM 流式输出 token 的机制完全同构。

opencode 的 `session.prompt()` 本身就是 SSE，机制底层已具备。MCP tool 调用流式化也是协议明确支持的。

### 为什么当前做不了

SSE 方案的硬前提是 **单次任务时长 < 5 分钟**，否则连锁问题：

1. **任务时长本身就过长**：当前 30 分钟与 5 分钟上限差 6 倍。让用户在对话窗口同步等 30 分钟，无论是否流式输出，都反 agent 直觉
2. **网关 / 反代 timeout 杀不住**：nginx 默认 60s，调到 300s（5min）已是合理上限。30min 长连接极易在中途被任何一层网关、代理、负载均衡器切断
3. **Electron 客户端连接保持成本**：30 分钟长连接对桌面 app 不友好 —— 断网重连、系统休眠、进程切换、网络环境变化（VPN / WiFi 切换）都可能中断；中断后需要复杂的重连 + 续传机制，已经不是"单 turn 同步等待"那么简单
4. **错误恢复路径复杂**：30 分钟内任一时刻连接断了，是重连还是退化为轮询查 task_id？退化为轮询就意味着这个方案不是纯 SSE，是 SSE + 任务管理的混合，复杂度反而高于纯任务管理方案
5. **UXR 服务端当前协议形态**：UXR 已实现的是"调用即返回 task_id + 后续轮询查询" 的异步任务模式（[mcp-contract.md](../specs/agents/mcp-contract.md)），改为 SSE 流式需要他们重写工具实现，且需要他们先解决任务时长本身

**根因**：SSE 不可行的根本原因是 **任务时长 30 分钟** 这个事实，而时长是 UXR 服务端的工程化能力决定的（单 KEY 排队、模型推理速度、文档解析效率），客户端无法独立优化。

### 后端如何让 SSE 变可行

UXR 服务端需要先做到：
- 单次分析稳定 < 5 分钟（理想 3 分钟）
- MCP tool 实现支持 SSE 流式响应（协议层已就绪，是 UXR 工具实现的事）

**一旦这两个条件达成**，对话流直接流式渲染，2.3 / 2.1 / 主进程轮询全部失去存在意义。**这是本产品长期演化的目标方向，但当前阶段无法依赖**。

---

## 在"SSE 做不了"前提下的候选方案

既然 SSE 在 5 分钟阈值未达成前不可行，需要在以下几个次优方案中选：

### 方案 2.1 — 任务面板 + API 轮询

**形态**：触发业务工具后生成任务卡片，右侧面板自动打开 tab，前端通过 HTTP API（与 MCP get_task_result / stop_task 同源数据）轮询，完成时面板内渲染结果。多文件结果点击在面板新开 sub-tab。

**优点**：
- 解决"自动展示进度"诉求
- 轮询走 API 不污染 LLM context
- 不消耗 LLM 调用 quota
- 多文件多卡片有展示空间

**问题**：
1. **轮询的归属层级模糊**：面板内轮询意味着"用户不打开面板就不会更新"，与"自动展示进度"的初衷矛盾。要消除这个矛盾，需要把轮询移到不依赖任何 UI 的位置（Electron 主进程），但这就升级到了"主进程轮询形态"，超出 2.1 的尺度
2. **聊天栏直接轮询不可行**：对话流是 turn-based，自动轮询会污染 LLM context 或产生"幽灵 turn"（无用户输入的 LLM 响应）。多任务并行时 N 个卡片各自轮询导致 UI 闪动；关闭对话窗口或切换 session 后轮询就停了
3. **面板语义冲突**：InsightPage 现有右侧面板是文件预览用途，混入任务进度后语义混乱，需要重新设计面板分层
4. **决策点数量多**：跨 session 任务可见性、任务历史保留策略、多任务并行布局、面板和对话联结、状态同步等 8+ 个决策点要逐一拍板
5. **形态是中间态**：2.1 解决了"独立呈现"，没解决"轮询归属""跨 session""不打开就不更新"；其问题向前推一步是主进程轮询，向后退一步是 2.3

### 方案 2.2 — 对话内静默 API 轮询

**形态**：生成任务卡片，对话流内自动 API 轮询，完成时把结果"塞"回对话。

**死结**：
- 完成时塞结果到原卡片位置 → 用户得回滚找，违反对话线性时间直觉
- 完成时塞到对话末尾 → 打断用户当前话题，且与当前 context 不相关
- 完成时不动对话只提示 → 那"在对话里轮询"就纯多余，**退化成 2.1**

所有可能演化路径都通向 2.1 或更差。淘汰。

### 方案 2.3 — 任务卡片刷新按钮（LLM 触发）

**形态**：任务卡片上加"刷新"和"终止"按钮。点击刷新 → 前端 inject 一条"查询 task_id=xxx 进度"提示词 → LLM 调 `get_task_result` MCP 工具 → 卡片就地更新状态。3 分钟防抖避免高频。

**优点**：
- 工期最低
- 决策点最少（防抖时长、按钮位置）
- 完全符合 [mcp-contract.md §LLM 调用规范](../specs/agents/mcp-contract.md)（"绝不在 LLM 内部自动轮询，由用户在对话中显式触发"）
- 可逆性高，未来 SSE 或主进程轮询升级时不堵路
- 不引入新后端 API（只用现有 MCP 工具）

**缺点**：
- token / context 浪费：用户主动刷 + 3 分钟防抖，累积有限；完成后用户不再刷
- 主动查询体验未达设计师"自动展示进度"诉求

### 主进程轮询形态 — Electron 后台 TaskWatcher + 全局任务托盘

**形态**：

```
Electron 主进程 (Octo 在跑就持续运行)
  ├─ TaskWatcher: 后台轮询所有进行中任务（SQLite 持久化）
  ├─ 完成 / 失败 → IPC 推送到所有 renderer
  └─ UI 层（对话流卡片 / 全局任务托盘 / 任务详情页）纯渲染，从 IPC + SQLite 拿数据
```

**它解决什么**：
- 用户离开当前对话窗口（切 session / 关再开 Octo）后，仍能知道任务完成
- 跨 session 任务汇总（任务托盘）

**它不解决什么**：
- **follow-up 机制和 2.3 / 2.1 一样**：用户基于结果追问时，仍是"前端 inject prompt → LLM 调 get_task_result"。主进程轮询只是多了"任务托盘"这个跳转入口
- 它解决的是"被动知道完成"，不解决"如何呈现进度"这个核心问题

**问题**：
- 核心价值（跨 session 汇总）在当前用户量小、跨 session 任务低频的阶段意义有限
- 复杂度是 2.3 的 10 倍：Electron 主进程改造 + 全局 UI 组件 + IPC + 持久化层
- 适合做这套的时机：用户量起来 + 长任务变常态 + 团队愿意投入 1-2 工程师月

### 关于 subAgent

讨论中提出"用 subAgent 隔离 context"。结论：**subAgent 在本场景能力不够**。

subAgent 本质是**主 agent 一次 turn 内的同步阻塞子任务**，生命周期是"主 agent 等它"的瞬间。它无法：
- 后台持续跑（turn 结束就结束）
- 完成时主动通知主 agent（必须主 agent 同步等它返回）
- 后台轮询 + 完成时插入对话（这需要主进程定时器 / Service Worker，不是 subAgent 能做的事）

subAgent 在本场景仅能"单次查询的中间过程不污染主 context"，2.3 防抖到位后这点污染本就可控，不值得多一层复杂度。

---

## 决策

**当前阶段采纳 2.3**：任务卡片刷新按钮 + LLM 触发查询。

理由（按消除法）：

1. **最佳方案 SSE 当前做不了**：根因是任务时长 30 分钟 远超 5 分钟阈值，连带网关 timeout、客户端连接保持、错误恢复等都做不到。这是 UXR 后端工程化能力决定的，客户端无法独立优化
2. **2.2 死结淘汰**：对话流自动轮询完成后无论怎么呈现结果都有死结
3. **主进程轮询解决的不是核心痛点**：它解决"被动知道完成"，不解决"如何呈现进度"；且复杂度过高，适合用户量大、长任务变常态时再做
4. **2.1 是中间状态**：它的形态问题（轮询归属 / 跨 session / 不打开就不更新）最终需要升级到主进程轮询才能解决；现在做 2.1 等于做一半，后面还要重做
5. **2.3 是 SSE 不可行时的最务实选择**：契约本身就是按此规范化的、决策点少、可逆性高、不堵未来升级路径

## 后果

### 必须做

- 任务卡片 UI（识别 MCP 返回的 `structuredContent.task_id`，在对话流渲染状态卡片）
- 刷新 / 终止按钮 + 3 分钟防抖
- 卡片状态更新（pending / processing / completed / failed / stopped）渲染
- completed 时复用现有 OutputCard 渲染 text part + resource_link

### 不做

- 任务面板（独立 UI 模块）
- 自动轮询机制（前端任何形态的定时器）
- 跨 session 任务列表 / 任务托盘
- 主进程 TaskWatcher
- 后端额外 HTTP API（只用现有 MCP 工具）

### 升级路径

**首选演化目标：SSE 流式**。当 UXR 服务端把单次分析时长压到 < 5 分钟 + MCP tool 改为 SSE 流式响应后，对话流直接流式渲染，2.3 / 任务卡片 / 刷新按钮全部移除。

**次选演化目标：主进程轮询形态**。仅在 SSE 路径长期无法达成且下列条件触发时考虑：
- 用户量增长至数百人，30 分钟排队成为常态
- 长任务变成业务核心场景（用户每天提交多个）
- 出现明显跨 session 任务管理需求

**不做 2.1 中间状态** —— 它的形态问题本质都指向"主进程轮询"，做了 2.1 还要再做一遍。

### 真正的根本优化方向

**这件事比任何前端方案都更值得优先**：和 UXR 团队对齐 5 分钟阈值。

需要 UXR 团队回答：
1. 30 分钟瓶颈具体在哪？（LLM 推理 / 排队 / 文档解析 / 哪个环节）
2. 压到 5 分钟内的可行路径？（模型换 / 并发 / 缓存 / 流式预解析）
3. 如果不可行，UXR 团队基于什么场景判断 30 分钟可接受？
