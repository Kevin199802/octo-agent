# ECharts能力边界与告知

使用ECharts或基于它的业务组件实现时，在承诺方案和编写代码前，按目标版本、可访问的官方文档、实际接口或必要的最小验证核对关键能力。无需每次展示完整能力表；存在限制或未知项时主动说明。

## 判断方式

| 情况 | 处理 |
| --- | --- |
| 内置能力适用 | 使用目标版本的真实配置/API；代码存在与交互验证分别记录 |
| 内置图形不足，但可用custom series等扩展 | 说明需要自定义实现及验证，不因“没有现成图表类型”直接称ECharts做不了 |
| 需要Vue/浏览器/其他工具配合 | 明确能力分工。例如右键菜单、浮窗与窗口拖动通常在界面层实现，图表层处理绘制、尺寸响应和可用的导出接口；这不等于整体需求不可实现 |
| ECharts支持，业务封装未开放或接口未知 | 说明是封装/接入限制，列出所需接口与内部验证项；不推定内部已有，也不将其说成ECharts本身缺能力 |
| 有依据确认在目标技术条件下无法实现 | 告知具体功能、依据和影响，提出可行替代或明确保留缺口，不能静默换方案或用无作用控件冒充完成 |
| 缺资料、缺运行条件或尚未验证 | 写“待确认/未验证”并说明缺什么；不能因未知或一次实现失败断言不支持 |

核对技术能力与业务条件：缺原始样本导致无法生成真实密度，属于数据缺口；浏览器权限导致无法复制图片，属于宿主条件；均不能直接归为ECharts缺陷。不编造技术承诺或内部API。

## 告知内容与时机

发现关键限制时及时向用户说明：**哪项需求 → 哪一层受限及依据 → 可以怎么实现/替代 → 对设计、依赖或接入有什么影响**。开发中发现新限制及时更新，不等到用户验收才暴露。

需要外部技术补足但仍能按原设计完成时，可在既定技术范围内继续实现并说明分工；替代方案明显改变分析含义、关键交互或用户指定技术栈时，说明差异并取得用户选择。独立可完成的部分继续推进。

交付时在最终说明和工程[HANDOFF.md](handoff.md)保留影响使用或接入的限制、补充技术和未验证项；无工程的输出在交付说明中记录。未完成的功能不能写成已支持，采用补充技术后不能声称全部由ECharts独立实现。普通代码错误应修复，不通过“能力不支持”掩盖。
