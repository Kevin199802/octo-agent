# 评价规则

先记录实际任务、所用规则版本、产物和检查证据。每项执行状态用“通过 / 失败 / 未执行 / 不适用”；未执行不计通过。仅评价用户要求、方案承诺及输出实际包含的能力。

| 维度 | 核对要点 |
| --- | --- |
| 路由与任务 | 正确识别目标；选适用方法，直接路径不强套方法卡 |
| 方法保真 | 适配时保留首选载体；用户指定或任务例外有据，不用规范覆盖度决定选图 |
| 数据语义 | 原值、单位、时间、缺失与身份可追溯；变换和参照口径明确 |
| 业务边界 | 无自造综合评分、权重、阈值、事实事件或已确认根因 |
| 规范 | 沿用已有适用定义；缺口和任务取舍如实说明，不冒充正式规则 |
| 可执行性 | 建议能指导设计；要求原型时，图形及承诺交互实际可用 |
| 证据 | 区分示例/真实数据、源代码能力、实际运行和业务集成结果 |

## 质量结论

- **PASS**：本次必需检查均有通过证据，且关键语义、任务和规范无冲突。
- **PARTIAL**：主要方案成立，但存在必需项未执行、未完成或说明不充分；列出具体缺口。
- **FAIL**：主任务错误，或发生数据/业务语义失真、无理由覆盖适用首选、虚构规范/API/验证结果等关键问题。

纯文字方案按其范围判断，不要求浏览器证据；代码产物的静态PASS不能自动升级为交互或业务接入PASS。缺专项规范本身不降级，也不要求L0/L1标签；但已知适用规则仍应核对，真实偏离须说明。
